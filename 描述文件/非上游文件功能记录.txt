================================================================================
一、文件类型区分
================================================================================

  A-type：mod 特有文件，上游无同名对应
    → 不受 gen-patches/check-patches 检查
    → 上游更新时不会被覆盖，但可能因上游导出变化而 SyntaxError
    → 更新策略：以新版上游为基准重建 + 保留 mod 特有逻辑

  B-type：mod 覆盖上游同名文件（overrides/ 目录）
    → 受 gen-patches/check-patches 检查（SHA-256 指纹比对）
    → 上游更新时可能 [CHANGED]，需手动合并
    → 更新策略：diff 上游新版 vs mod 版本，合并上游新逻辑 + 保留 mod 改动

二、mod-framework/（框架层）
================================================================================

  ── mod-framework/lib/patcher.js ──
    功能：运行时文件替换器
    机制：启动时从各 mod 的 overrides/ 目录读取文件，用完整内容替换
          Node.js require 缓存中的上游文件
    路径映射：
      mods/<mod>/overrides/server/xxx.js → Stronghold-Protocol/server/xxx.js
      mods/<mod>/overrides/shared/xxx.js → Stronghold-Protocol/shared/xxx.js
      mods/<mod>/overrides/public/xxx.js → Stronghold-Protocol/public/xxx.js

  ── mod-framework/modHook.js ──
    功能：事件总线
    API：
      on(name, fn)    注册监听器
      emit(name, ...args)  触发事件
      hook(name, fn)  注册拦截器（可修改/阻止原始行为）
    上游文件中的调用方式：
      import modHook from '../../../mod-framework/modHook.js';
      modHook.emit('businessHook', ...);

  ── mod-framework/scripts/gen-patches.js ──
    功能：指纹生成
    机制：为 mod 的每个 override 文件，计算对应上游源文件的 SHA-256，
          存入 mods/<mod>/patches/fingerprint.json

  ── mod-framework/scripts/check-patches.js ──
    功能：兼容性检查
    机制：读取 fingerprint.json 中的 SHA-256，与当前上游源文件比对，
          输出 [OK] / [CHANGED] / [MISSING] 状态

  ── mod-framework/modManager.js ──
    功能：mod 加载器
    机制：读取 mods/ 目录，按配置启用/禁用 mod，调用 mod 的 install() 函数
    基于上游添加（2026-10-30）：
      · CLI 工具静默：当 process.argv[1] 是 tools/ 下的脚本（如 tools/plugin.mjs check --json）时，
        过滤掉以 [mod: / [modManager] 开头的 console.log 行，其余日志照常输出
        原因：modHook.js 会自动加载 modManager.js，工具脚本的 stdout 会被 mod 加载日志污染，
              调用方解析 --json 输出时 JSON.parse 失败
    更新上游时注意：必须保留 CLI 工具静默逻辑，否则 test/check-status.test.js 会失败

  ── mod-framework/modServer.js ──
    功能：mod 文件服务 + 服务器入口
    机制：HTTP 请求时按 reverse load order 返回 mod 的 public/ 文件
    加载顺序：clementia → clone → dupBand → 20p
    文件服务优先级：mod-framework > 20p > dupBand > clone > clementia
    路径映射：
      mod-framework/public/ → / (最高优先级，统一 room.js/CSS)
      mod/<mod>/public/    → / (mod 特有客户端文件)
      mod/<mod>/shared/    → /shared/ (mod 共享代码)
      mod/<mod>/overrides/ → / (覆盖上游文件，server/→/server/, js/→/js/)

  ── mod-framework/check-mods.js ──
    功能：mod 启用检测（供 .bat 调用）
    机制：检查 config.json 中是否有 mod 启用
    退出码：0 = 至少一个 mod 启用，1 = 无 mod 启用或配置不存在

  ── mod-framework/config-ui.js ──
    功能：mod 配置 Web UI
    机制：启动临时 HTTP 服务器，打开浏览器页面供用户启用/禁用 mod，
          保存 config.json 后退出。在主服务器启动前调用

    mods/玩法/20p/overrides/server/match/match/votes.js（⚠ 新增，上游无此文件）
      功能：20p 三个半数通过投票（2026-10-28 加时/跳过，2026-10-29 新增倍速）
      机制：导出 Match20pVotes 类，由 Match.js 挂到 Match 原型链上，方法包含
            · _handle20pVote(ps, msg) — 六条 C2S 意图的分发入口（platform.js 调用）
            · requestPrepExtend / votePrepExtend — 休整期加时（+30s / +60s）
            · requestUniteSkip / voteUniteSkip — 联防跳过
            · requestSpeedUp / voteSpeedUp — 战斗倍速（mul ∈ SPEED_MULS = {1, 2}）
            · _openVote — 发起收口：发起人票数已达阈值则直接生效，否则挂超时并广播
            · _voteSeats / _voteNeed / _vote / _endVote / _expireVote — 投票管道
            · _applyPrepExtend / _applyUniteSkip / _applySpeedUp — 通过后的生效逻辑
      关键规则：
            · 半数阈值 = ceil(在座且在线的人数 / 2)，发起人自动计为同意
            · 拒绝只剔除该席位，剩余可同意席位不足半数时才结束投票
            · 投票窗口 20s（scaled），超时自动取消
            · 加时每个休整期一次（_prepExtendRound），无 deadline 的休整期拒绝
            · 跳过按 _uniteLeft 统计的在场敌人数扣血（与结算同一上限），
              场上敌人直接清除、不给任何资金/击杀，随后走原 settle()，
              合成结果 res 只带 perPlayer[pid].leaked，不带 coins/killed
            · 倍速是整局状态（_speedMulState 记当前倍数，_speedBase 记起始时钟）：
              首次生效时把当时的 gameSpeed 存为 _speedBase，之后
              gameSpeed = min(200, _speedBase × mul)，回 1× 时精确还原原速
              （测试局的自定义 combatSpeed 因此不会被乘两次）
            · 倍速只影响 COMBAT / 联防 / boss 三阶段（它们的 deadline、
              客户端 b.start 的 speed、加时消耗都读 gameSpeed）；
              休整期与选阵倒计时读自己的计时器，不受影响
            · 倍速只能在 PREP 发起（战斗进行中改 gameSpeed 会让服务端 deadline
              与客户端已下发的 speed 错位）；当前倍数已等于目标倍数时拒绝
            · 同一休整期内两个 PREP 投票（加时 / 倍速）互斥，同时只开一个
            · 重复提交守卫：发起人已在 agreed，再次提交同意返回 'already voted'；
              已拒绝者重复拒绝同样被拒（服务端强制，不依赖 UI 隐藏按钮）
      更新上游时注意：如果上游新增同名 votes.js 需合并；否则保留此文件
                      （依赖 Match 的 humans/_uniteLeft/_stopClientCombat/
                        setDeadline/prepDeadline/settle/later/cancel 等公开方法，
                        以及核心层 gameSpeed 字段——上游若重命名该字段，
                        _applySpeedUp 必须同步改名）

  ── _patch_versions.mjs ──

    机制：读 data/backups.json + data/garrisons.json（默认版本）作为基准

            battle_equip_table / activity_table.autoChessData）
    生成的规则（与 build-data.mjs 一一对应）：
      · 表单归属：stand-in 补位干员获得所有引用它的 chess 记录的状态；
                  DIY 原型干员获得它服务的 tier 的全部 slot 及 golden 记录状态；
                  owned 自选池干员获得全部 DIY 槽位状态
      · statusKey = `<phase>/<level>/<skillLevel>/<equipLevel>`，与 chess.json 槽位 status 匹配
      · 召唤物变体：buildDiyTokens 只为自选干员的召唤物生成 `<charId>@<statusKey>`，
                    只写 backups.tokens，绝不碰 tokens.json（避免一个 token 两条记录）
      · 自选池规范化：legal6 `!roster.has(id)` —— 剔除本版本 chess.json 已引用的固定干员
      · 富文本：garrison/skill/talent 同时写 desc（纯文本，已剥 <@ba.vup> 等标签）
                与 descRaw（完整富文本，交客户端 RichText 解析）
    三种运行模式：
      node _patch_diy.mjs           → check（只报告，不写盘）
      node _patch_diy.mjs patch     → 写入三个版本
      node _patch_diy.mjs verify    → 校验：每个 DIY 状态都有表单/变体、各模块集合一致
