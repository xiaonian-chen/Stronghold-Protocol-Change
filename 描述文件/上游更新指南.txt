===========================================================
  完整更新流程（五层递进）
===========================================================

★ 重要：上游使用 GitHub Releases 发布稳定版，只合并打了 tag 的版本！
   先浏览器打开 https://github.com/sganggs/Stronghold-Protocol/releases
   看到新版本号（如 v0.3.2）再开始以下流程。

★ 逻辑：先合代码 → 再统一版本 → 再验功能 → 再验框架 → 再验 mod
  每一层都依赖前一层完成，不能跳过。


───────────────────────────────────────────────
  第一层：核心合并（Git 自动）
───────────────────────────────────────────────

  ★ 参考文件：
    · 核心层改动记录.txt → 第一层：列出所有可能冲突的 22 个文件及保留策略
    · 非上游文件功能记录.txt → 第七节：上游更新时功能保留检查清单

  ── 1.0 发现新版本 ──

    方式一（推荐）：浏览器打开 Releases 页面看版本号
    方式二（订阅）：页面右上角 Watch → Custom → 勾选 Releases，自动邮件通知

  ── 1.1 拉取 + 预览 ──

    cd d:\yjw\Stronghold-Protocol-v0.3.3\Stronghold-Protocol
    git fetch upstream --tags
    git log HEAD..v0.3.2 --oneline
    git diff HEAD..v0.3.2 --stat

  ── 1.2 合并 ──

    git merge v0.3.2

  ── 1.3 解决冲突（如有）──

    只有我们修改过的 12 个文件可能出现冲突：
      server/lobby.js              scripts/launch.mjs
      server/match/Match.js        server/match/match/phases.js
      server/match/player/economy.js   server/match/finalAssault.js
      server/sim/content/bands/meta.js
      public/js/ui/detailPanel.js  public/js/render/app.js
      data/garrisons.json          shared/constants.js
      public/css/screens/sweep.css  public/js/ui/hud.js

    解决策略见下方「冲突处理指南」。
    解决完后：git add . ; git commit -m "merge upstream v0.3.2"

  ── 1.4 版本差异采集（★★★ 产出第二层的排查清单！）──

    合并提交完成后，用 git 精确获取"本次上游版本相对旧版改了哪些文件"，
    生成第二层只针对这些文件排查的清单。此步骤能让第二层从"全量扫"
    变为"按 git 清单精准扫"，既省时又零遗漏。

    第一步：记录旧版本 tag（首轮已是 v0.3.1-base）：
      git tag                                        # 查看已有 tag
      若本轮更新前没有给当前 HEAD 打 tag，先打上：
        git tag v0.3.1-base 或对应旧版本号 <旧tag>

    第二步：提取"改动的文件"清单：
      git diff <旧tag>..<新tag> --name-only
      例如：git diff v0.3.1-base..v0.3.2 --name-only

    第三步：提取"新增/删除的文件"清单：
      git log <旧tag>..<新tag> --name-status --diff-filter=ADR
      # A=新增 R=重命名 D=删除，--name-status 输出每行以 状态+文件名 开头

    第四步：合并清单，去重后保存为「本次版本漂移排查清单」，
      供第二层使用。删除的文件（D）通常无需排查（本地已被移除），
      但要确认 20p 是否曾对该文件做过 override——若有，需确认 override
      同步移除，避免残留失效文件。

    注意：
      · 清单只包含"上游本次改动的文件"，即唯一可能发生版本漂移的对象
      · 未在清单中的文件 = 上游没改，行数/哈希天然一致，无需浪费精力
      · 20p 自身新增、与上游无同名交集的 A-type 文件不在漂移范围，
        仍交给第三层功能验证（详见下方边界说明）


───────────────────────────────────────────────
  第二层：版本漂移排查（★★★ 核心合并后立即执行！）
───────────────────────────────────────────────

  ★ 参考文件：
    · 核心层改动记录.txt → 第二层：需检查的非上游文件清单（mod-framework/public/ + 各 mod A-type）
    · 非上游文件功能记录.txt → 各 mod 节：每个 A-type/B-type 文件基于上游添加了什么逻辑，
                             "更新上游时注意"标注必须保留的内容
    · 功能适配经验.txt → 1.3/1.4：版本漂移排查经验（B-type 不报错但 UI 异常、
                                             A-type 误覆盖导致功能丢失）

  问题本质：
    mod-framework/public/ 和 mods/*/public/ 下的文件会覆盖上游同名文件。
    如果这些文件基于旧版上游，新版 UI 结构/样式/逻辑会异常，
    且不报 SyntaxError——旧版有完整导出，只是渲染结果与新版不匹配。
    这是比导出缺失更隐蔽的兼容性问题。

  目的：
    核心合并完后，立即确保所有非原版文件都基于新版上游，
    消除版本漂移，为后续各层的功能验证提供正确的基础。
    这是整个流程中最关键的一步——跳过会导致后续所有验证都在错误基准上进行。

  排查范围：
    ★ 本层已精简为"只针对 1.4 版本差异采集生成的清单"排查，
       不再全量扫所有非上游文件。

    清单中的文件 = 上游本次改动 + 需确认的 20p override 映射：
      先从「本次版本漂移排查清单」取出每个改动文件（去掉 server/ 核心层、
      纯新增的 A-type），单列出其中"与上游有同名对应文件"的那些（即 mod-
      framework/public/、mods/*/public/、mods/*/overrides/ 下的覆盖文件），
      用下方的五步递进逐一排查。

    边界（明确哪些不归本层管）：
      · 纯新增的 A-type 文件（上游没有同名文件，纯 mod 增加）
        → 不在漂移范围，本层跳过 → 交给第三层功能验证
      · server/ 核心层改动文件
        → 合并阶段已由 git 处理冲突，本层只关注 public/ 与 overrides/ 的
          UI/逻辑覆盖文件
      · 未出现在清单中的覆盖文件
        → 上游没改，行数/哈希天然一致，无需排查

  排查优先级（仍遵循）：
    mod-framework/public/ > mods/*/public/ > mods/*/overrides/
    （mod-framework 优先级最高，影响面最大）
    清单内全部文件都要过，但优先级高者先查、给更多关注。

  排查方法（五步递进）：

    ── 第一步：行数对比 ──

      对每个 mod 文件，计算与上游同名文件的行数差异：
        差异 ≤ 5 行  → 低风险（可能只是微调）
        差异 6-50 行 → 中风险（需进一步检查）
        差异 > 50 行 → 高风险（很可能基于旧版或有大量 mod 扩展）

      PowerShell 脚本示例：
        $mod = "mod-framework\public\js\screens\bandDraft.js"
        $up  = "Stronghold-Protocol\public\js\screens\bandDraft.js"
        $modLines = (Get-Content $mod).Count
        $upLines  = (Get-Content $up).Count
        Write-Host "$mod : mod=$modLines upstream=$upLines diff=$(modLines - $upLines)"

    ── 第二步：关键特征 grep ──

      从上游新版新增的 CSS class、组件名、函数名、常量名中，
      选取代表性关键词，在 mod 文件中搜索。
      如果上游有但 mod 文件没有 → 确认基于旧版。

      常用关键词（v0.3.2 新增）：
        CSS class:  dorder__card, dorder__art, dorder__face, rs-clock__ver,
                    protocol-boot, draft-detail__off
        组件/函数:  VersionTag, AiTakeoverPanel, heldDraftPub,
                    DRAFT_HOLD_MS, BOOT_MIN_MS, useRise

      PowerShell 脚本示例：
        $features = @('VersionTag', 'DRAFT_HOLD_MS', 'dorder__card')
        foreach ($f in $features) {
          $inUp  = (Get-Content $up -Raw) -match [regex]::Escape($f)
          $inMod = (Get-Content $mod -Raw) -match [regex]::Escape($f)
          Write-Host "$f : upstream=$inUp mod=$inMod"
        }

    ── 第三步：哈希校验 ──

      对行数完全一致的文件，计算 SHA-256 哈希：
        哈希一致 → 文件与上游完全相同，无风险
        哈希不一致 → 内容有差异，需人工对比

      PowerShell 脚本示例：
        $h1 = (Get-FileHash $mod -Algorithm SHA256).Hash
        $h2 = (Get-FileHash $up  -Algorithm SHA256).Hash
        Write-Host "identical: $($h1 -eq $h2)"

    ── 第四步：重写函数完整性检查（★★★ 前三步通过仍可能有此问题！）──

      前三步只能检测"mod 文件是否缺少上游新增内容"，无法检测
      "mod 重写的函数是否丢失了上游原有功能"。
      override 文件重写上游函数时，如果只保留了自己用到的模式，
      丢失了其他调用方依赖的模式，会导致静默失效（不报错，但功能缺失）。

      检查方法：
        对每个 override 文件，提取其中重写/覆盖的上游函数名，
        与上游同名文件中对应函数逐一对比：
          a) 函数签名（参数列表）是否一致
          b) 功能分支是否完整（if/else/switch 所有分支）
          c) 返回值类型/结构是否一致

      重点检查的函数类型：
        - 被多个系统调用的公共 API（rollPool、rollItemId、grantChess 等）
        - 事件 handler / dispatch 函数
        - 数据访问函数（gameData、chess、band 等）

      历史案例：
        20p spDraft.js 的 rollPool()：原版支持 weighted/items/默认池抽取
        三种模式，20p override 只保留了 items 模式，导致歌蕾蒂娅特质、
        焰尾特质、潘格尼尼策略全部失效（它们使用默认池抽取模式）
        详见功能适配经验.txt → 0.11

    ── 第五步：分组/分池逻辑共享属性一致性检查 ──

      分组/分池逻辑中，如果每组独立调用"包含随机决策的完整生成函数"，
      会导致各组结果不一致（如 family 不同）。

      检查方法：
        对每个 override 文件中的分组/分池循环（poolGroups.map / forEach），
        检查循环体内是否调用了包含随机决策的完整生成函数（如 generateDraft）：
          a) 如果是，提取随机决策到循环外，先统一决定共享属性
          b) 循环内只做"基于已决定的共享属性生成具体内容"

      历史案例：
        20p spDraft.js 的 enterSpDraft()：对每个 poolGroup 独立调用
        generateDraft()，而 generateDraft 内部每次独立 weightedPick 决定
        family，导致 A 组全道具/B 组全悬赏/C 组全战术
        修复：先统一 weightedPick 决定 family，再为各组用 buildCards()
        生成同 family 卡牌
        详见功能适配经验.txt → 0.12

  本层工作流总结（精简版）：
    1. 第 1.4 步已生成「本次版本漂移排查清单」
    2. 从清单中筛出"与上游有同名覆盖"的文件（排除纯新增 A-type 与
       server/ 核心层，它们归别的层）
    3. 对筛出的文件，按需套用五步递进：
       第四/五步是重点（重写完整性 + 分组一致性），
       第一/二/三步在当前"清单导向"下可直接聚焦差异文件用，
       不再需要全量哈希核对。
    4. 修复遵循下方「修复策略」

  修复策略（按 mod 改动量选择）：

    a) mod 无特有改动
       → 直接用上游替换
       例：mod-framework/game.js（纯旧版覆盖，无 mod 逻辑）

    b) mod 仅有 1-2 处改动
       → 用上游替换 + 手动加回改动
       例：dupBand/bandDraft.js（上游 + const taken = new Map()）

    c) mod 有大量特有改动
       → 以上游为基准，逐个合并新增功能
       例：mod-framework/room.js（保留 20p/clone 模式切换，
           合并 VersionTag 等新功能）

    d) mod-framework/public/ 文件同时有 mod 特有功能
       → 用上游替换 + 重新添加 mod 特有逻辑
       例：mod-framework/bandDraft.js（上游 + clone draft 投票逻辑）

  ── 4.1 检查 patcher.js 运行时替换 ──

    mod-framework/lib/patcher.js 负责把 overrides/ 文件替换到运行时内存。
    原理：启动时读取 overrides/ 下的文件，用其完整内容替换上游文件。
    只要 overrides 里覆盖的文件路径在上游仍然存在，patcher 就正常。

    极端情况：如果上游删除了某个被 overrides 覆盖的文件，patcher 会在
    控制台打印 [patcher] MISSING 警告，此时需要评估该 override 是否废弃。

  ── 4.2 检查 modHook.js 钩子系统 ──

    mod-framework/modHook.js 是事件总线，提供：
      modHook.on('hook:name', callback)   → 注册钩子
      modHook.emit('hook:name', ...args)  → 触发钩子

    我们打在上游文件里的 emit 调用（如 modHook.emit('match:start', match)）
    已经由 Git 合并保护——只要合并时保留了我们的 emit 行就没事。

    如果上游改了调用时机（比如 match:start 不再在某个位置触发），需人工
    查看 git diff 确认 emit 所在上下文是否被破坏。

  ── 4.3 检查 gen-patches / check-patches 工具 ──

    这两个脚本依赖上游文件结构。如果上游改了目录组织，可能需要微调。
    正常情况下不会出问题——先跑一下看看有无报错即可。

  ── 4.4 确认 modManager.js 加载正常 ──

===========================================================
  冲突处理指南
===========================================================

当 git merge 报 CONFLICT 时：

  a) 冲突原因
     上游和我们各自修改了同一个文件的同一行/相邻行。
     Git 无法自动决定用哪个版本，需要人工裁决。

  b) 查看冲突
     git status                        → 列出所有冲突文件
     git diff                           → 查看冲突内容（<<<<<< ======= >>>>>>>）

  c) 解决策略（按文件）
     ──────────────────────────────────────────────────────────────
     server/lobby.js             保留 businessHook/modHook，上游新功能合并
     server/match/Match.js       保留 modHook emit
     server/match/player/economy.js  保留 _effectiveShopSlots() 包装函数
     server/match/match/phases.js    保留 hook emit
     server/match/finalAssault.js    保留 bossHp hook
     server/sim/content/bands/meta.js  保留 duckReplace hook
     scripts/launch.mjs           保留 20p-loader --import 入口
     public/js/ui/detailPanel.js  保留 desc||descRaw（非 descRaw||desc）
     public/js/render/app.js      保留 ++layerPopSeq + _flags 透传
     data/garrisons.json          保留 clementia 数据记录
     shared/constants.js          保留 ROOM_CAPACITIES 和 DEFAULT_SEATS 导出
     public/css/screens/sweep.css 保留上游新版（我们无特有改动）
     public/js/ui/hud.js          保留联防轮次条件渲染
     ──────────────────────────────────────────────────────────────

  d) 解决完所有冲突
     git add .
     git commit -m "merge upstream <版本号>"

         精确提取上游本次改动的文件清单
      b) 第二层精简为"只针对清单排查"，未在清单的文件=上游没改，
         行数/哈希天然一致，无需浪费精力
      c) 明确边界：纯新增 A-type 归第三层、server/ 核心层由 git 合并处理
    - 价值：从"全量扫"变"按 git 清单精准扫"，更省时且零遗漏
      （git 直接给真相，比行数对比/哈希的"反向推断"更可靠）
