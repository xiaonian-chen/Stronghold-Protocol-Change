  ── 1.3 解决冲突（如有）──

    只有我们修改过的 14 个文件可能出现冲突：
      server/lobby.js              scripts/launch.mjs
      server/match/Match.js        server/match/match/phases.js
      server/match/host/index.js   server/match/player/economy.js
      server/match/finalAssault.js

      data/garrisons.json          shared/constants.js
      public/css/screens/sweep.css  public/js/ui/hud.js

    其中 server/match/host/index.js 的冲突是 2026-10-31 新增的
    （版本主机 fork 追加父进程 --import 钩子），合并时必须保留
    inheritedImportFlags / importFlagValue 及 kind === 'version' 分支的
    钩子追加；若上游改用了 worker 或新的启动封装，要把同样的传递接回去，
    否则三个非默认版本会静默退回原版（详见核心层改动记录 [25]）。

    解决策略见下方「冲突处理指南」。
    解决完后：git add . ; git commit -m "merge upstream v0.3.2"

  ── 1.4 版本差异采集（★★★ 产出第二层的排查清单！）──

    合并提交完成后，用 git 精确获取"本次上游版本相对旧版改了哪些文件"，
    生成第二层只针对这些文件排查的清单。此步骤能让第二层从"全量扫"
    变为"按 git 清单精准扫"，既省时又零遗漏。

    第一步：记录旧版本 tag（首轮已是 v0.3.1-base）：
      git tag                                        # 查看已有 tag
      若本轮更新前没有给当前 HEAD 打 tag，先打上：
        git tag v0.3.1-base 或对应旧版本号 <旧tag>

    第二步：提取"改动的文件"清单：
      git diff <旧tag>..<新tag> --name-only
      例如：git diff v0.3.1-base..v0.3.2 --name-only

    第三步：提取"新增/删除的文件"清单：
      git log <旧tag>..<新tag> --name-status --diff-filter=ADR
      # A=新增 R=重命名 D=删除，--name-status 输出每行以 状态+文件名 开头

    第四步：合并清单，去重后保存为「本次版本漂移排查清单」，
      供第二层使用。删除的文件（D）通常无需排查（本地已被移除），
      但要确认 20p 是否曾对该文件做过 override——若有，需确认 override
      同步移除，避免残留失效文件。

    注意：
      · 清单只包含"上游本次改动的文件"，即唯一可能发生版本漂移的对象
      · 未在清单中的文件 = 上游没改，行数/哈希天然一致，无需浪费精力
      · 20p 自身新增、与上游无同名交集的 A-type 文件不在漂移范围，
        仍交给第三层功能验证（详见下方边界说明）

  ── 1.5 上游符号依赖核对（★ 2026-10-29 新增，源自 20p 倍速投票实战）──

    背景：mod 新功能常常"不修改任何上游文件，而是复用上游已有的字段/方法"
          （如 20p 倍速投票直接读写 Match.gameSpeed）。这类功能在
          git merge 时零冲突、在 gen-patches 时零告警，
          但如果上游重命名/删除该字段，功能会**静默失效**（不报错）。

    做法：从「非上游文件功能记录.txt」中每个文件的「更新上游时注意」
          段落里，提取"依赖上游符号"的条目，汇总成一张依赖表；
          再把依赖表与 1.4 的改动清单取交集。

    当前已登记的上游符号依赖（随功能增加持续追加）：

      符号名            所属上游文件                          使用方
      gameSpeed         server/match/Match.js（初始化+clamp）   20p votes.js _applySpeedUp
      this.humans       server/match/Match.js                 20p votes.js _voteSeats
      setDeadline()     server/match/match/*.js               20p votes.js / unitePhase.js
      prepDeadline      server/match/match/phases.js          20p votes.js 加时
      settle()          server/match/match/*.js               20p votes.js 跳过
      _uniteLeft        overrides/match/unitePhase.js         20p votes.js 跳过扣血
      b.start.speed     server/match/match/clientCombat.js    倍速客户端表现（只读）
      _startMsg         server/match/match/clientCombat.js    倍速客户端表现（只读）
      fork() 参数       server/match/host/index.js             版本主机启动（钩子传递依赖）
      execArgv          server/match/host/index.js             版本主机启动（--import 追加位置）

    核对方法（PowerShell）：
      $old = 'v0.3.2'; $new = 'v0.3.3'
      git diff $old..$new -- server/match/Match.js server/match/match/clientCombat.js `
                            server/match/host/index.js
      # 重点看 gameSpeed / humans / setDeadline / settle / fork 参数 / execArgv
      # 是否被重命名或改签名

    判定：
      · 符号仍在且签名未变 → 该功能无需适配，跳过
      · 符号被重命名       → 必须同步修改使用方（如 _applySpeedUp 内的 gameSpeed）

  第二层：版本漂移排查（★★★ 核心合并后立即执行！）
───────────────────────────────────────────────

  ★ 参考文件：
    · 核心层改动记录.txt → 第二层：需检查的非上游文件清单（mod-framework/public/ + 各 mod A-type）
    · 非上游文件功能记录.txt → 各 mod 节：每个 A-type/B-type 文件基于上游添加了什么逻辑，
                             "更新上游时注意"标注必须保留的内容
    · 功能适配经验.txt → 1.2/1.3：版本漂移排查经验（B-type 不报错但 UI 异常、
                                             A-type 误覆盖导致功能丢失）
    · 功能适配经验.txt → 1.4：版本主机子进程不继承 --import（切版本后 mod 静默失效）
    · 功能适配经验.txt → 2.22~2.26：倍速投票暴露的"增量状态漂移 / 阶段边界 /
                                      上游符号复用"三类新经验
    · 1.5 产出的「上游符号依赖表」：清单内文件若命中表中符号，优先核对

  问题本质：
    mod-framework/public/ 和 mods/*/public/ 下的文件会覆盖上游同名文件。
    如果这些文件基于旧版上游，新版 UI 结构/样式/逻辑会异常，
    且不报 SyntaxError——旧版有完整导出，只是渲染结果与新版不匹配。
    这是比导出缺失更隐蔽的兼容性问题。

  目的：
    核心合并完后，立即确保所有非原版文件都基于新版上游，
    消除版本漂移，为后续各层的功能验证提供正确的基础。
    这是整个流程中最关键的一步——跳过会导致后续所有验证都在错误基准上进行。

  排查范围：
    ★ 本层已精简为"只针对 1.4 版本差异采集生成的清单"排查，
       不再全量扫所有非上游文件。

    清单中的文件 = 上游本次改动 + 需确认的 20p override 映射：
      先从「本次版本漂移排查清单」取出每个改动文件（去掉 server/ 核心层、
      纯新增的 A-type），单列出其中"与上游有同名对应文件"的那些（即 mod-
      framework/public/、mods/*/public/、mods/*/overrides/ 下的覆盖文件），
      用下方的五步递进逐一排查。

    边界（明确哪些不归本层管）：
      · 纯新增的 A-type 文件（上游没有同名文件，纯 mod 增加）
        → 不在漂移范围，本层跳过 → 交给第三层功能验证
      · server/ 核心层改动文件
        → 合并阶段已由 git 处理冲突，本层只关注 public/ 与 overrides/ 的
          UI/逻辑覆盖文件
      · 未出现在清单中的覆盖文件
        → 上游没改，行数/哈希天然一致，无需排查

  排查优先级（仍遵循）：
    mod-framework/public/ > mods/*/public/ > mods/*/overrides/
    （mod-framework 优先级最高，影响面最大）
    清单内全部文件都要过，但优先级高者先查、给更多关注。

  排查方法（五步递进）：

    ── 第一步：行数对比 ──

      对每个 mod 文件，计算与上游同名文件的行数差异：
        差异 ≤ 5 行  → 低风险（可能只是微调）
        差异 6-50 行 → 中风险（需进一步检查）
        差异 > 50 行 → 高风险（很可能基于旧版或有大量 mod 扩展）

      PowerShell 脚本示例：
        $mod = "mod-framework\public\js\screens\bandDraft.js"
        $up  = "Stronghold-Protocol\public\js\screens\bandDraft.js"
        $modLines = (Get-Content $mod).Count
        $upLines  = (Get-Content $up).Count
        Write-Host "$mod : mod=$modLines upstream=$upLines diff=$(modLines - $upLines)"

    ── 第二步：关键特征 grep ──

      从上游新版新增的 CSS class、组件名、函数名、常量名中，
      选取代表性关键词，在 mod 文件中搜索。
      如果上游有但 mod 文件没有 → 确认基于旧版。

      常用关键词（v0.3.2 新增）：
        CSS class:  dorder__card, dorder__art, dorder__face, rs-clock__ver,
                    protocol-boot, draft-detail__off
        组件/函数:  VersionTag, AiTakeoverPanel, heldDraftPub,
                    DRAFT_HOLD_MS, BOOT_MIN_MS, useRise

      PowerShell 脚本示例：
        $features = @('VersionTag', 'DRAFT_HOLD_MS', 'dorder__card')
        foreach ($f in $features) {
          $inUp  = (Get-Content $up -Raw) -match [regex]::Escape($f)
          $inMod = (Get-Content $mod -Raw) -match [regex]::Escape($f)
          Write-Host "$f : upstream=$inUp mod=$inMod"
        }

    ── 第三步：哈希校验 ──

      对行数完全一致的文件，计算 SHA-256 哈希：
        哈希一致 → 文件与上游完全相同，无风险
        哈希不一致 → 内容有差异，需人工对比

      PowerShell 脚本示例：
        $h1 = (Get-FileHash $mod -Algorithm SHA256).Hash
        $h2 = (Get-FileHash $up  -Algorithm SHA256).Hash
        Write-Host "identical: $($h1 -eq $h2)"

    ── 第四步：重写函数完整性检查（★★★ 前三步通过仍可能有此问题！）──

      前三步只能检测"mod 文件是否缺少上游新增内容"，无法检测
      "mod 重写的函数是否丢失了上游原有功能"。
      override 文件重写上游函数时，如果只保留了自己用到的模式，
      丢失了其他调用方依赖的模式，会导致静默失效（不报错，但功能缺失）。

      检查方法：
        对每个 override 文件，提取其中重写/覆盖的上游函数名，
        与上游同名文件中对应函数逐一对比：
          a) 函数签名（参数列表）是否一致
          b) 功能分支是否完整（if/else/switch 所有分支）
          c) 返回值类型/结构是否一致

      重点检查的函数类型：
        - 被多个系统调用的公共 API（rollPool、rollItemId、grantChess 等）
        - 事件 handler / dispatch 函数
        - 数据访问函数（gameData、chess、band 等）

      历史案例：
        20p spDraft.js 的 rollPool()：原版支持 weighted/items/默认池抽取
        三种模式，20p override 只保留了 items 模式，导致歌蕾蒂娅特质、
        焰尾特质、潘格尼尼策略全部失效（它们使用默认池抽取模式）
        详见功能适配经验.txt → 0.11

    ── 第五步：分组/分池逻辑共享属性一致性检查 ──

      分组/分池逻辑中，如果每组独立调用"包含随机决策的完整生成函数"，
      会导致各组结果不一致（如 family 不同）。

      检查方法：
        对每个 override 文件中的分组/分池循环（poolGroups.map / forEach），
        检查循环体内是否调用了包含随机决策的完整生成函数（如 generateDraft）：
          a) 如果是，提取随机决策到循环外，先统一决定共享属性
          b) 循环内只做"基于已决定的共享属性生成具体内容"

      历史案例：
        20p spDraft.js 的 enterSpDraft()：对每个 poolGroup 独立调用
        generateDraft()，而 generateDraft 内部每次独立 weightedPick 决定
        family，导致 A 组全道具/B 组全悬赏/C 组全战术
        修复：先统一 weightedPick 决定 family，再为各组用 buildCards()
        生成同 family 卡牌
        详见功能适配经验.txt → 0.12

  ── 4.1 检查 patcher.js 运行时替换 ──

    mod-framework/lib/patcher.js 负责把 overrides/ 文件替换到运行时内存。
    原理：启动时读取 overrides/ 下的文件，用其完整内容替换上游文件。
    只要 overrides 里覆盖的文件路径在上游仍然存在，patcher 就正常。

    极端情况：如果上游删除了某个被 overrides 覆盖的文件，patcher 会在
    控制台打印 [patcher] MISSING 警告，此时需要评估该 override 是否废弃。

  ── 4.2 检查 modHook.js 钩子系统 ──

    mod-framework/modHook.js 是事件总线，提供：
      modHook.on('hook:name', callback)   → 注册钩子
      modHook.emit('hook:name', ...args)  → 触发钩子

    我们打在上游文件里的 emit 调用（如 modHook.emit('match:start', match)）
    已经由 Git 合并保护——只要合并时保留了我们的 emit 行就没事。

    如果上游改了调用时机（比如 match:start 不再在某个位置触发），需人工
    查看 git diff 确认 emit 所在上下文是否被破坏。

    这两个脚本依赖上游文件结构。如果上游改了目录组织，可能需要微调。

当 git merge 报 CONFLICT 时：

  a) 冲突原因
     上游和我们各自修改了同一个文件的同一行/相邻行。
     Git 无法自动决定用哪个版本，需要人工裁决。

  b) 查看冲突
     git status                        → 列出所有冲突文件
     git diff                           → 查看冲突内容（<<<<<< ======= >>>>>>>）

  c) 解决策略（按文件）
     ──────────────────────────────────────────────────────────────
     server/lobby.js             保留 businessHook/modHook，上游新功能合并
     server/match/Match.js       保留 modHook emit
     server/match/player/economy.js  保留 _effectiveShopSlots() 包装函数
     server/match/match/phases.js    保留 hook emit
     server/match/finalAssault.js    保留 bossHp hook
     server/sim/content/bands/meta.js  保留 duckReplace hook
     server/match/host/index.js   保留 inheritedImportFlags + 版本 fork 追加 --import
     scripts/launch.mjs           保留 20p-loader --import 入口
     public/js/ui/detailPanel.js  保留 desc||descRaw（非 descRaw||desc）
     public/js/render/app.js      保留 ++layerPopSeq + _flags 透传
     data/garrisons.json          保留 clementia 数据记录
     shared/constants.js          保留 ROOM_CAPACITIES 和 DEFAULT_SEATS 导出
     public/css/screens/sweep.css 保留上游新版（我们无特有改动）
     public/js/ui/hud.js          保留联防轮次条件渲染
     ──────────────────────────────────────────────────────────────

  d) 解决完所有冲突
     git add .
     git commit -m "merge upstream <版本号>"

17. 单仓库多分支发布结构（方案 A）（2026-10-31，2026-11-01 调整为分支配对）
    背景：子模块 Stronghold-Protocol/ 历史上一直以「上游 commit + 未提交脏工作树」
          的形式存在于本机；v1.0 / v1.1 / v1.2 / v1.3.1-beta / v1.3.2-beta /
          v1.3.3-beta（旧）所有 tag 的 gitlink 都指向本机私有 commit（从未推送），
          .gitmodules 的 url 又是相对路径 ./Stronghold-Protocol
          → 从 GitHub 下载的测试版/稳定版解压后子模块目录为空，
            缺全部游戏本体 + 核心层改动（含 [25] 版本主机钩子继承），双击必失败

    约束：GitHub 仓库的 ZIP 下载永远不含子模块内容，
          换任何仓库结构都改变不了这一点（必须靠 Releases 挂完整 zip 才能双击即玩）

    方案（一个仓库 URL，根目录分支与游戏本体分支配对）：
      仓库：https://github.com/xiaonian-chen/Stronghold-Protocol-Change.git
        main       稳定版根目录 —— mods/、mod-framework/、描述文件/、node/、启动脚本
        text       测试版根目录 —— 同结构，功能领先 main
        core-text  text 对应的游戏本体快照 —— Stronghold-Protocol/ 全部文件
                   34751 文件 / 199.6 MB / 快照 commit bf97326d6（v1.3.3-beta）
        core-main  预留，发稳定版时才创建
      命名规则：根目录分支 X ↔ 游戏本体分支 core-X
      .gitmodules：
        [submodule "Stronghold-Protocol"]
            path = Stronghold-Protocol
            url = https://github.com/xiaonian-chen/Stronghold-Protocol-Change.git
            branch = core-text
      → git clone --recurse-submodules 一条命令拿到全部内容，不需要第二个仓库

    ⚠ 为什么加 -text 后缀：原来的 core 实际只服务测试版，命名看不出归属；
      加后缀后每个根目录分支都有明确对应的游戏本体分支，
      发稳定版时新建 core-main，不会误把稳定版 gitlink 指到测试快照

    ⚠ 历史命名变更（2026-11-01）：core → core-text
      操作顺序必须先建后删：git push origin core:core-text
      → git branch -m core core-text → git branch -u origin/core-text
      → git push origin --delete core
      原因：bf97326d6 当时只被 core 一个分支引用，
            先删 core 会让该 commit 变不可达 → 克隆时找不到 → 子模块为空

    子模块 remotes（并存，互不干扰，更新路径未切断）：
      upstream  https://github.com/sganggs/Stronghold-Protocol.git   原作者，更新用
      origin    本仓库 core-text 分支                                发布用

    core-text 快照制作流程（每次上游更新后执行一次，详见非上游文件功能记录第十节）：
      1) 子模块内 git fetch upstream --tags
      2) 在已合并完成的分支上走完本指南五层流程
      3) git checkout core-text
      4) git read-tree -u --reset <已合并完成的分支>   ← 用合并后的树替换工作树
      5) git add -A && git commit -m "core: vX.Y.Z 游戏本体快照（上游 <tag> + 核心层改动）"
      6) git push origin core-text
      7) 主仓库 git add Stronghold-Protocol 更新 gitlink → 提交 text

    发稳定版时（新增 core-main）：
      1) text 测试通过 → 主仓库合并 text → main
      2) 子模块 git checkout -b core-main core-text
      3) 稳定版核心与测试版一致：直接 git push origin core-main（同一 commit，零传输）
      4) 不一致：在 core-main 上重新做快照并提交
      5) 主仓库 .gitmodules 的 branch 改为 core-main，gitlink 指向 core-main 的 commit
      6) 打稳定版 tag 并推送

    ⚠ 快照必须是「链」：父提交 = core-* 上一次快照。每次新建孤立根提交会导致
      远端没有基准对象，每次都要全量重传

    ⚠ 首次推送代价实测：约 790 MB。远端快照分支为空、没有上游历史基准，
      本地按上游历史做的增量压缩 blob 必须全部还原成完整对象再发送。
      后续快照以上一次快照为父 → 远端已有基准 → 推送量回到 MB 级

    ⚠ 历史 tag 已清理（2026-11-01）：v1.0 / v1.1 / v1.2 / v1.3.1-beta / v1.3.2-beta
      五个 tag 的 gitlink 指向本机私有 commit，下载后子模块必为空；
      且核心层已改动、旧 tag 对应的核心目录不复存在，无法也不需要还原
      → 本地与远端一次性删除这 5 个 tag，只保留 v1.3.3-beta
      → 待 v1.3.3-beta 测试通过后，从当前状态重新发布稳定版
      → 以后每个新 tag 必须确认 gitlink 指向对应 core-* 分支上的 commit 且远端可查

    验收：
      · git ls-remote origin core-text 返回快照 commit（不是只存在于本机）
      · 主仓库 git submodule status 显示的 commit == 远端 core-text HEAD
      · 全新目录 git clone --recurse-submodules 后 Stronghold-Protocol/ 非空
      · 子模块 git fetch upstream --tags 仍正常（原作者更新路径不受影响）
      · Releases 挂本机打包的完整 zip（含 node/），GitHub 自动源码包不能直接玩

    - 价值：从"全量扫"变"按 git 清单精准扫"，更省时且零遗漏
      （git 直接给真相，比行数对比/哈希的"反向推断"更可靠）
