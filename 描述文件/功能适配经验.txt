################################################################################
【零】上游版本更新（0.3.1 → 0.3.2）
################################################################################

  ── 0.1 mod-framework/public/ 文件版本漂移 ──
    现象：策略选择界面 UI 异常（缺少 dorder__card 分离式布局等 v0.3.2 新增结构）
    根因：mod-framework/public/ 下的 bandDraft.js/game.js/room.js 基于 v0.3.1 旧版，
          优先级最高覆盖上游同名文件，但不报 SyntaxError（旧版有完整导出）
    修复：用 v0.3.2 上游替换 + 手动加回 mod 特有逻辑
    经验：mod-framework/public/ 文件版本漂移是最隐蔽的兼容性问题——
          不报错但 UI 结构/样式与新版不匹配。上游更新后必须全量检查

  ── 0.2 版本漂移排查误覆盖 A-type 文件 ──
    现象：20p 分组悬赏 UI 消失，显示原版上游 UI
    根因：版本漂移排查时将 20p 的 A-type 特有文件（spDraft.js/choiceOverlay.js/
          game-panels.css）误当作 B-type 覆盖
    修复：重建三个核心文件
    经验：A-type（mod 特有，上游无同名对应）永远不应被版本漂移排查覆盖；
          B-type（覆盖上游同名文件）才需要做版本基准检查

  ── 0.3 20p 客户端文件导出缺失 ──
    现象：报 SyntaxError: does not provide an export named 'heldDraftPub'
    根因：20p 的 public/ 文件基于 v0.3.1，缺少 v0.3.2 新增导出
    修复：所有 20p 客户端文件替换为 v0.3.2 上游 + 保留 20p 特有逻辑
    经验：A-type 客户端文件上游更新时必须全面同步，以新版为基准重建

  ── 0.4 clementia diyModel.js diyPrefKey 导出缺失 ──
    现象：报 SyntaxError: does not provide an export named 'diyPrefKey'
    根因：clementia diyModel.js 基于 v0.3.1，缺少 v0.3.2 新增导出
    修复：以 v0.3.2 上游为基准重建 + 保留 _flags 透传逻辑
    经验：A-type 文件上游更新时必须全面同步，不能只修报错的那一个导出

  ── 0.5 clementia diy.js UI 异常 ──
    现象：自选编队选择干员界面显示异常
    根因：clementia diy.js 基于 v0.3.1 旧版 UI 架构，缺少 v0.3.2 新组件/布局
    修复：整体替换为 v0.3.2 上游 + 在详情面板插入 _flags 切换代码
    经验：上游 UI 重构时 mod 的 A-type 屏幕文件必须整体更新

  ── 0.6 sweep.css Git 合并冲突标记残留 ──
    现象：点击 S.W.E.E.P. 报告后界面完全异常，无样式渲染
    根因：sweep.css 文件中残留 16 处未解决的 Git 合并冲突标记
          （<<<<<<< HEAD / ======= / >>>>>>> v0.3.2），浏览器无法
          解析这些 Git 标记语法，导致整个 CSS 文件解析失败
    修复：用上游 0.3.2 版本的 sweep.css 直接覆盖（冲突双方中
          v0.3.2 侧为正确版本，HEAD 侧为旧版）
    经验：Git 合并冲突标记残留在 CSS/JS 文件中是最隐蔽的 UI 破坏源——
          不报 SyntaxError（CSS 容错解析），但整文件样式全部失效。
          合并上游更新后必须全量搜索 <<<<<<< / ======= / >>>>>>> 标记

  ── 0.7 modServer.js 重复启动逻辑 ──
    现象：main() 函数和 if(isProcessEntry) 入口块重复了服务器启动+handler包装逻辑
    根因：重构时 main() 提取不完整，入口块保留了独立启动代码，
          导致 main() 成为死代码且缺少错误处理/信号处理/浏览器打开
    修复：合并为单一 main() 函数，入口块仅调用 main()
    经验：代码提取重构时必须确认原入口点完全委托给新函数

  ── 0.8 Match.js delete this.gd.factions 后续访问崩溃 ──
    现象：禁用飞行开关生效后，后续 waves.js 访问 gd.factions 得到 undefined
    根因：2.8 修复中用 delete this.gd.factions 恢复原 getter，
          但后续代码仍通过 this.gd.factions 访问数据，delete 后得到 undefined
    修复：改为保存原始 factions 对象，setupMatchWaves 执行后
          用 Object.defineProperty 恢复原始值，而非 delete
    经验：delete 恢复 getter 的前提是后续无代码通过该属性访问数据

  ── 0.9 teamPanel.js 版本漂移（20p 客户端）──
    现象：20p teamPanel.js 比 0.3.2 上游少 34 行，缺失上游新增功能
    根因：20p override 基于 v0.3.1 旧版，只添加了分页逻辑
    修复：上游替换 + 注入 20p 分页逻辑（poolGroupSizes/pagePlayers/nav）
    经验：mod 的客户端 override 文件同样需要版本漂移排查

  ── 0.10 setupVote.js 缺少 _rerollStartAt.clear() ──
    现象：完成重投后冷却时间不清除，玩家无法再次发起重投
    根因：20p override 基于 v0.3.1，缺少 v0.3.2 新增的
          this._rerollStartAt.clear()
    修复：在 completeSetupReroll 的 this.setupVote = null 后添加
          this._rerollStartAt.clear()
    经验：B-type override 不仅要保留 mod 特有逻辑，
          还必须同步上游新增的功能逻辑

  ── 0.11 override 重写函数功能残缺（rollPool 丢失默认池抽取模式）──
    现象：歌蕾蒂娅特质（获得斯卡蒂/幽灵鲨/深巡）、焰尾特质（获得野鬃/灰毫/远牙）、
          潘格尼尼策略（刷新获得拉特兰）全部不触发
    根因：20p override 的 spDraft.js 中 rollPool() 只实现了 items 数组模式，
          缺少 weighted 加权模式和默认池抽取模式（this.pool.roll），
          而歌蕾蒂娅/焰尾/潘格尼尼使用的池（pool_char_abyssal/pool_char_kazimierz/
          pool_char_later）均为默认模式（bond+minTier 过滤），rollPool 返回 null
    修复：将原版 rollPool 完整实现（支持 weighted/items/默认三种模式）
          复制到 20p spDraft.js
    经验：override 重写上游函数时，必须逐一对比函数签名和功能完整性，
          不能只保留"自己用到的"模式。被 garrison/band 等系统调用的
          公共 API（rollPool/rollItemId 等）必须支持上游的所有调用模式

  ── 0.12 分组机变 family 不一致（各组随机到不同卡牌类型）──
    现象：9 人 3 组机变阶段，A 组 6 张全是装备/道具，B 组 6 张全是悬赏，
          C 组 6 张全是战术，同回合各组卡牌类型完全不同
    根因：20p enterSpDraft() 的分组逻辑对每个 poolGroup 独立调用
          generateDraft()，而 generateDraft() 内部每次都独立做
          weightedPick 随机决定 family（bounty/supply/shop/tactic），
          导致各组随机到不同的 family
    修复：先统一用 weightedPick 决定 family，再为各组用 buildCards()
          生成同 family 的卡牌（每组卡牌内容可不同但类型一致）；
          同时导出 choices.js 的 scheduleFor/buildCards/formatCount/FAMILY_NAMES
    经验：分组/分池逻辑中，"先统一决定共享属性、再各自生成具体内容"是
          基本原则。每组独立调用"包含随机决策的完整生成函数"会导致
          各组结果不一致。应将随机决策提取到分组循环之外

################################################################################
【二】20p mod（玩法扩展）
################################################################################

  ── 2.1 ROOM_CAPACITIES is not defined ──
    现象：创建 20 人同盟报 ReferenceError
    根因：20p overrides/shared/protocol.js 遗漏了 ROOM_CAPACITIES 导入
    修复：import 语句添加 ROOM_CAPACITIES
    经验：B-type override 更新时必须完整对比上游的 import 列表

  ── 2.2 首领限伤开关不生效 ──
    现象：关闭开关后高伤害干员打首领仍被限伤
    根因：限伤逻辑全链路有多个断点（lobby dispatch 缺 case、Match 未读 rules、
          damage.js 未读 flags）
    修复：完整实现 UI → C2S → 服务端 → rules → flags → 引擎 全链路
    经验：功能开关必须走完整链路验证，任何一环缺失都会导致功能不生效

  ── 2.3 悬赏分组异常 + 无时间限制 + 选择卡住 ──
    现象：玩家分到错误组、无 30s 倒计时、主机选择不了界面卡住
    根因：enterSpDraft() 自行切片 humansOrder 而非使用 this.poolGroups；
          _startGroupTurn 缺少 deadline 设置
    修复：改用 this.poolGroups 分配玩家 + 添加 deadline 超时逻辑
    经验：分组逻辑必须使用 poolGroups（按座位分配的权威分组），
          不能自行切片。poolGroupSizes 只提供大小不包含玩家分配

  ── 2.4 联防阶段轮次 UI 缺失 ──
    现象：阶段胶囊只显示"联防"，不显示轮次（如"联防 1/3"）
    根因：服务端 views.js 已输出 round/roundsMax，但客户端 hud.js 未消费
    修复：hud.js 条件渲染 "联防 X/Y"
    经验：服务端输出 → 客户端读取 → UI 渲染，三环缺一不可

  ── 2.5 match:init 双触发导致时序问题 ──
    现象：clone mod 先以 4p 模式初始化，然后 20p 触发第二次
    根因：Match.js 构造函数和 platform.js start() 都触发 match:init
    修复：移除构造函数中的 match:init + 直接在构造函数中设置 this._20pActive = true
    经验：match:init 只应在 start() 中触发一次。其他 mod 需要读取的字段
          应在构造函数中直接设置，不依赖 match:init 钩子

  ── 2.6 禁用飞行类敌人开关不生效 ──
    现象：开启禁用飞行开关后开始模拟，随机选的 3 种敌人类型仍包含飞行类
    根因：原实现仅后置过滤已生成的 factions，但 setupMatchWaves 内部随机
          已基于原始 involveRandom 列表完成选取，后置过滤无法改变已选结果
    修复：改为在调用 setupMatchWaves 前临时排除飞行 type——通过
          Object.defineProperty 在 gd 实例上定义 own property 遮蔽原型
          factions getter，使 setupMatchWaves 读取到不含飞行 type 的
          factions，调用后 delete 恢复原 getter
    经验：随机选取逻辑必须在随机发生前修改候选集，后置过滤无效。
          要影响 setupMatchWaves 的行为，必须在它读取数据前修改数据源

  ── 2.7 禁用飞行开关：冻结对象无法修改（第一次报错）──
    现象：开启禁用飞行开关弹服务器内部错误
          TypeError: Cannot assign to read only property 'involveRandom' of object
    根因：factions.types 中的对象被 Object.freeze 深度冻结，直接赋值
          involveRandom = false 报错
    修复：创建 types 数组的浅拷贝，对需要禁用的飞行 type 创建新对象
          { ...original, involveRandom: false } 替换冻结对象
    经验：游戏数据对象被深度冻结（Object.freeze），不能直接修改属性。
          需要修改时必须创建新对象替换，保持原冻结对象不变

  ── 2.8 禁用飞行开关：冻结对象无法修改（第二次报错）──
    现象：修复 2.7 后仍报 TypeError: Cannot assign to read only property 'factions'
    根因：尝试直接修改 gd.raw.factions 替换整个 factions 对象，但
          gd.raw 本身也被 Object.freeze 冻结，无法赋值
    修复：放弃修改 gd.raw，改用 Object.defineProperty 在 gd 实例上
          定义 own property 'factions' 遮蔽原型 getter。这样
          setupMatchWaves 读取 this.gd.factions 时拿到修改后的 factions，
          调用后 delete this.gd.factions 恢复原 getter
    经验：当整条数据链路都被冻结时，不能用赋值方式修改任何层级。
          Object.defineProperty 在实例上定义 own property 是遮蔽原型
          getter 的有效手段，无需复制大量内部函数代码，且无随机数
          序列副作用

  ── 2.9 悬赏决策界面无法选择（客户端字段名错误）──
    现象：分组悬赏决策界面点击选项无反应，所有卡牌不可选
    根因：choiceOverlay.js:118 构造 groupSp 时字段名错误：
          activeGroup.turn → undefined（normalizeSpGroups 返回的字段名
          是 turnPid），导致 cardPickable 始终返回 false
    修复：activeGroup.turn → activeGroup.turnPid
    经验：数据结构字段名变更时必须全量搜索消费方。normalizeSpGroups
          的输出字段名与直觉不同（turnPid 而非 turn），容易遗漏

  ── 2.10 悬赏分组人机不选/阶段卡死（服务端全局 token/deadline 冲突）──
    现象：多组同时启动时，先启动的组 bot 不选、deadline 不触发，阶段卡死
    根因：两个并发 bug 叠加——
          Bug A：_startGroupTurn 和 _scheduleGroupBot 都用 ++this._turnToken
          生成 token，多组同时启动时后设置的 token 覆盖前面的，先启动的
          组回调执行时 token !== this._turnToken → 直接 return
          Bug B：setDeadline 内部 this.cancel(this._phaseTimer) 取消前一个
          timer，多组同时有人类玩家时后设置的 deadline 覆盖前面的，前面组
          的超时回调被取消
    修复：1. 每个组使用独立的 g._turnToken，各组互不干扰
          2. 分组模式下用 this.later 代替 this.setDeadline 调度 deadline，
          timer 存在 g._turnTimer 上
          3. _applyGroupCard 中玩家选牌后取消当前组的 timer
          4. _checkGroupsDone 中所有组完成时取消所有组的 timer
          5. views.js 序列化每个组的 turnDeadline，客户端用当前活动组的
          deadline 显示倒计时
    经验：多组并发时全局 token/timer 是经典的竞态条件源。每组必须有独立
          的 _turnToken 和 _turnTimer，单组模式走上游逻辑不受影响

  ── 2.11 悬赏界面完全不可用（客户端+服务端双 bug 叠加）──
    现象：悬赏决策界面点击不了、人机不选、阶段卡死——完全不可用
    根因：2.9（客户端字段名错误导致 cardPickable=false）和
          2.10（服务端全局 token/deadline 冲突导致 bot 不选/超时不触发）
          两个 bug 同时存在，客户端不可选 + 服务端不推进 = 完全卡死
    修复：分别修复 2.9 和 2.10
    经验：界面完全不可用时往往有多个独立 bug 叠加。客户端 bug 阻止用户
          操作，服务端 bug 阻止自动推进，两者同时存在才会完全卡死。
          排查时必须分别验证客户端逻辑和服务端逻辑

  ── 2.12 局内左侧组切换按钮点击不了 ──
    现象：6人以上分组模式，局内左侧队伍面板的组切换按钮点击无反应
    根因：.team 父容器 CSS 设置了 pointer-events: none（穿透点击到下层战场），
          但 .team__nav 子元素没有 pointer-events: auto 覆盖，
          导致导航按钮也继承 none 无法点击
    修复：添加 .team__nav { pointer-events: auto } CSS 规则
    经验：pointer-events: none 穿透设计时，所有需要交互的子元素都必须
          显式设置 pointer-events: auto。CSS 继承是隐式的，容易遗漏

  ── 2.13 悬赏选项点击不了（turnPid 字段映射错误）──
    现象：20人分组模式，主机和朋友的悬赏决策界面选项都点击不了
    根因：choiceOverlay.js 中 cardPickable 和 armedCard 判断使用了
          顶层 sp 对象（无 turnPid），而非当前组的 turn 对应玩家。
          pickSp 函数虽然正确但未被调用
    修复：统一使用 pickSp 并正确映射 turn 字段到 turnPid
    经验：分组模式下"当前轮到谁选择"的信息在组的 turn 字段中，
          不能用顶层 sp（那是全局状态，分组模式下无意义）。
          修复时必须确认所有判断点都使用了正确的数据源

  ── 2.14 悬赏倒计时只有10秒 ──
    现象：分组悬赏决策倒计时约10秒就结束，正常应为每人30秒
    根因：spDraft.js 中 spFirst（首人选择时间）在分组模式下仍使用
          上游默认值（较短），而非统一的30秒
    修复：分组模式下 spFirst 统一设为 30s
    经验：分组模式下的计时逻辑应与分组设计意图一致（每人独立30s），
          不能沿用上游的非分组计时参数

  ── 2.15 联防第一轮结束直接结算 ──
    现象：20人5轮联防，第一轮倒计时结束就直接结算整个联防状态
    根因：unite.js 的 settle 调用没有检查是否还有后续轮次。
          nextUnitePlan 函数存在但从未被调用
    修复：新增 unitePhase.js override，拦截 settle 调用，
          实现 _uniteNextOrSettle：当前轮 < 总轮次 → 重置倒计时+推进轮次，
          当前轮 = 总轮次 → 执行原 settle
    经验：多轮次机制必须在"结算"动作前检查轮次状态。settle 是终态动作，
          不能直接调用，必须经过轮次检查。新增 override 文件
          unitePhase.js 比修改原 unite.js 更安全（不破坏上游逻辑）

  ── 2.16 组切换导航UI优化 ──
    现象：组切换按钮为上下箭头，分组X/X文本不明显，导航控件在头像下方
    根因：初始实现未考虑用户体验细节
    修复：1) 按钮改为左右箭头
          2) 分组X/X文本加粗加深（font-weight:700, color加深）
          3) 整个导航控件移到头像上方（DOM 顺序调整）
          4) 添加背景、圆角、hover 效果
    经验：分组导航是高频操作控件，必须醒目易用。上下箭头语义
          不如左右（翻页习惯），位置在上方更符合视觉层级

  ── 2.17 新增投票 C2S 意图被上游 intents.js 拦截 ──
    现象：客户端点击「加时 +30s」/「联防跳过投票」无反应（服务器回 BAD_MSG 或 ignored）
    根因：上游 intents.js 用固定的 msg.t 分发表，未知类型直接丢弃；
          仅在 protocol.js 注册 C2S 消息不足以让请求到达业务代码
    修复：1) shared/protocol.js 注册四条消息的 schema（g.prepExtend / g.prepExtendVote /
             g.uniteSkip / g.uniteSkipVote）
          2) platform.js 在交给 intents.js 之前先按 VOTE_TYPES 前置路由到
             _handle20pVote()（overrides 无法改上游分发顺序，只能前置拦截）
    经验：mod 新增的玩家意图必须"协议注册 + 前置路由"成对出现；
          只做其一会表现为"请求被静默丢弃"，且没有任何报错日志

  ── 2.18 20 人投票照搬全票制导致"一票否决" ──
    现象：加时/跳过投票只要有人点拒绝就立刻结束，20 人房几乎永远通不过
    根因：直接复用 setupVote.js 的全票通过模型（任一票反对即失败）
    修复：_voteNeed(vote) = ceil(在座在线人数 / 2)（发起人自动计为同意）；
          拒绝只把该席位加入 declined 并从 agreed 移除，
          仅当 agreed + 未表态席位 < 半数时才 _endVote 结束投票
    经验：大房间投票要区分"通过阈值"和"终止条件"。
          半数制下拒绝不是终止信号，而是减少可达成席位的计数，
          终止条件必须是"剩余可同意席位不足以达到阈值"
          （6 人房：1 票同意 + 3 票拒绝仍可继续，剩 2 席刚好够半数）

  ── 2.19 联防跳过投票通过后重复结算 / 二次进入联防 ──
    现象：跳过投票通过后，同一轮联防被结算两次，或跳过之后又开了一轮联防
    根因：跳过时先 runner.stop() 再 later(0) 调用 settle()，
          但 FieldRunner 在 instant 模式下已排队的 _runInstant 回调仍会执行，
          _runInstant 末尾的 _checkDone() 会触发 onDone → _uniteNextOrSettle，
          此时 phase 已推进到 SETTLE，迟到的回调仍按旧逻辑再推进/再结算一次
    修复：1) _applyUniteSkip 中 plan.skipRemaining = true（nextUnitePlan 返回 null）
          2) unitePhase.js 的 _uniteNextOrSettle 开头增加
             "phase === UNITE 且 plan === unitePlan" 双重匹配检查，不匹配直接 return
    经验：在"阶段推进"链路上做外部强制结束时，必须同时处理
          已排队但未执行的定时器回调（later(0) / instant 模式回调）。
          幂等检查要放在回调入口，而不是只在主动调用方加锁

  ── 2.20 联防跳过扣血数量与实际在场敌人不一致 ──
    现象：跳过时扣血数量偏多（把已经重新入场过的敌人又扣了一次）
    根因：结算用 uniteSurvivors(plan, res) 统计漏怪，它会把
          plan.notReentered 里"无法重新入场"的敌人再加一遍；
          而跳过要扣的是"此刻仍站在场上的敌人"（_uniteLeft）
    修复：合成结果 res 只带 perPlayer[pid].leaked（按 _uniteLeft 的占位漏怪构造），
          并传入 { ...plan, notReentered: new Map() } 给 settle，避免重复计数
    经验：同一个"漏怪数"在两处有不同口径——"本场总共漏了多少"（结算统计）
          和"此刻还剩几个"（跳过扣血）。复用结算函数时必须显式清空
          notReentered，否则会双重计数

  ── 2.21 投票发起人默认一票却还能重复投票 ──
    现象：申请人发起投票后（已自动计为同意），再点一次「同意」计数会 +1，
          导致 1 个人贡献 2 票，半数门槛被提前击穿
    根因：发起流程把 proposer 写进 vote.agreed，但 _vote() 入口没有做
          "该席位是否已表态"的校验——UI 上按钮还留着，服务端也照收
    修复：_vote() 第一行加守卫
            if (agree ? vote.agreed.has(ps.playerId) : vote.declined.has(ps.playerId))
              return fail(ERR.BAD_MSG, 'already voted')
          客户端同步：已答复者不再渲染按钮，改渲染「你已同意 / 你已拒绝」
    经验：幂等校验必须放在服务端业务入口，不能依赖客户端隐藏按钮
          （重放/多开/网络重试都能绕过 UI）。凡是有"自动预置状态"的流程
          （发起人自动同意、房主自动准备），都要假设客户端会重复提交

  ── 2.22 倍速投票直接改 gameSpeed 导致"越申请越快" ──
    现象：1× 申请 2× 后 gameSpeed 翻倍；再申请 2× 时 gameSpeed 又翻倍（4×）；
          回到 1× 后速度变成原速的一半
    根因：把 gameSpeed *= mul 当增量操作，没有保存"基准速度"；
          而测试局可能把初始 combatSpeed 设成非标准值（如 1.5），
          任何增量式的乘除都会累积误差
    修复：引入 _speedBase（首次生效时的原始 gameSpeed）与
          _speedMulState（当前倍数，初值 1）：
            gameSpeed = min(200, _speedBase × _speedMulState)
          每次投票只改 _speedMulState，再按上式重算，永远是"基准 × 倍数"，
          回 1× 时精确还原
    经验：实现"可反复切换的倍率"时，状态应该存"目标倍率 + 基准值"，
          而不是对当前值做增量运算。增量运算在往返切换中必然漂移

  ── 2.23 倍速在战斗中途生效导致服务端/客户端时钟错位 ──
    现象：战斗打到一半有人申请倍速通过，倒计时瞬间跳变，或动画与服务端
          deadline 对不上
    根因：战斗阶段客户端已按 b.start.speed 下载并开始本地动画，
          服务端 deadline 也已按旧 gameSpeed 算好；中途改 gameSpeed
          不会重新下发 speed，也不会重算 deadline
    修复：requestSpeedUp 只在 PREP 阶段允许（phase !== PREP 直接 fail），
          UI 在非 PREP 时显示「仅休整期可申请」
    经验：凡是"影响已下发计时/动画参数"的调整，只能在阶段边界做。
          战斗内的调速需要额外下发重同步消息，成本远高于"仅休整期可申请"

  ── 2.24 倍速投票与加时投票同时发起互相覆盖 ──
    现象：同一休整期内先发起加时投票，再发起倍速投票，前一个投票的 UI 消失
          但超时定时器还在跑
    根因：两个投票各自维护 this.prepExtendVote / this.speedUpVote，
          但 UI 只渲染其中一个；且两者都占用同一个休整期窗口
    修复：三个发起函数统一收口到 _openVote(vote, onPass)：
          进入前（在各 request 函数内）先检查"当前是否已有进行中的 PREP 投票"，
          有则拒绝新发起；_openVote 负责票数达阈值时直接生效、
          否则挂 timer + markPublic + flush，把这三段重复代码收进一处，
          避免各处实现不一致
    经验：同一时间窗内互斥的多个投票，必须有统一的"发起入口 + 占用检查"，
          不能让每个投票各自实现一套。收口后新增第三种投票只是加一个分支

  ── 2.25 倍速徽章放在战斗顶栏胶囊旁会覆盖上游 hud.js ──
    现象：最初设计把「战斗 ×2」徽章塞进战斗顶栏胶囊区域，
          需要改 public/js/ui/hud.js（核心层文件），上游每次升级都要重合并
    修复：改放到 mod 自有的 teamPanel.js（A-type 覆盖，上游无同名文件），
          常驻队伍面板顶部，整局可见且不与战斗 UI 抢位置
    经验：新 UI 优先放在 mod 自有文件里。核心层文件每多改一处，
          上游升级的合并成本就多一份；能用覆盖文件承接的绝不改核心层

  ── 2.26 倍速只影响战斗/联防/boss，不影响休整期 ──
    排查方法：确认三个阶段的倒计时来源
      · combat.js / unitePhase.js / bossRounds.js 的 deadline 均由 gameSpeed 折算 ✅
      · 休整期倒计时与选阵倒计时读 prepDeadline / 各自 turnTimer，不读 gameSpeed ✅
      · 客户端 b.start 的 speed 字段来自 clientCombat.js 的 _startMsg ✅
      → 因此改 gameSpeed 恰好只影响这三阶段的动画与倒计时，符合需求
    经验：确认"某个开关影响范围"时，不要只看变量名，要顺着
          "变量 → 谁读它 → 读它的人控制什么"走一遍全链路

             cache miss → fetch(request)，失败直接抛 TypeError，
             无重试无降级。一次瞬断导致整个页面生命周期内 3D 场景不可用
          2) 浏览器 HTTP 缓存：F5 使用缓存协商，如果缓存了异常响应
             则后续请求继续失败。硬刷新绕过缓存所以临时恢复
          3) 服务器压缩：.bin 文件被 brotli 压缩，主机 localhost
             支持 brotli（安全上下文），朋友 LAN IP 不支持（非安全上下文
             只支持 gzip）。brotli 压缩异常只影响主机，与"主机失败朋友正常"一致
    修复：三层加固——
          1) sw.js：3次重试循环，重试时 new Request(url, { cache: 'no-store' })
             绕过浏览器 HTTP 缓存
          2) load.js：fetchWithRetry 函数（2次重试）+ loadScenePack 整体
             3次重试（拆分为 loadScenePackCore + 外层循环）
          3) files.js：.bin 从 COMPRESSIBLE 移除，不再压缩二进制顶点数据
    经验：Service Worker 拦截请求后必须添加重试逻辑，否则一次网络瞬断
          就会导致整个页面生命周期内功能不可用。F5 无法恢复是因为 SW
          仍在控制页面，只有硬刷新（新 SW 生命周期）才能恢复。
          .bin 等大体积二进制文件压缩收益极小但增加出错风险，
          主机 localhost 支持 brotli 而朋友 LAN IP 不支持，
          压缩方式差异可能是"只有主机出问题"的根因之一

【六】通用经验速查
################################################################################

  1.  全链路思维：新增自定义字段时必须追踪从输入到输出的每一个构造点
  2.  缓存键完整性：缓存键必须包含所有影响结果的字段
  3.  静默失败最危险：INSTALLERS/patcher/cleanDiyPick 静默跳过不报错
  4.  mod-framework 兼容性：public/ 文件始终加载，不能依赖 mod 启用
  5.  gameMode 白名单：每种模式必须在 setGameMode 校验中注册
  6.  功能开关全链路：UI → C2S → 服务端 → rules → flags → 引擎
  7.  浏览器缓存陷阱：优先取每次重新读取的字段（desc > descRaw）
  8.  ESM 时序问题：top-level await 早于动态 import，需重新加载机制
  9.  A-type vs B-type：A-type（mod特有）不覆盖，B-type（覆盖上游）才检查
  10. 组件定义 ≠ 组件生效：定义 → 导入渲染 → CSS 定位，三步缺一不可
  11. 服务端输出 → 客户端消费 → UI 渲染，三环缺一不可
  12. OperatorImage ownerId：undefined=跟随时装，null=强制默认，playerId=指定玩家
  13. _flags 位掩码：修改时必须逐位确认所有组合
  14. garrisonIds 与特质面板：修改 bonds 不影响特质，必须同时设 garrisonIds
  15. C2S 协议注册：新增消息类型时必须注册，否则客户端发送被拦截
  16. 分组用 poolGroups：不能自行切片 humansOrder
  17. match:init 只触发一次：在 start() 中触发，字段在构造函数中直接设置
  18. 随机前修改候选集：后置过滤无效，必须在随机发生前修改数据源
  19. Object.freeze 冻结对象：游戏数据被深度冻结，修改需创建新对象替换
  20. Object.defineProperty 遮蔽 getter：整条链路冻结时，在实例上定义
      own property 遮蔽原型 getter，调用后 delete 恢复
  21. Git 合并冲突残留：合并上游后必须全量搜索 <<<<<<< / >>>>>>> 标记，
      CSS 中残留不报错但整文件样式失效
  22. 多 mod override 同一文件：后加载版本必须完整包含所有 mod 逻辑，
      遗漏不报错——静默失效
  23. 序列化函数字段保留：freezeDiy/Object.freeze 等必须保留所有自定义
      字段，新增字段时必须检查序列化路径
  24. garrisonIds 与 form 类型：DIY 干员有 normal/golden 两个 form，
      garrisonIds 必须根据 form 区分，不能只看 _flags
  25. garrisonIds 与 bonds 独立：garrisonIds（+1/+2）和 bonds（盟约类型）
      是两个独立维度，修改时分别确认对应关系
  26. 多组并发竞态：每组必须有独立的 _turnToken 和 _turnTimer，
      全局 token/timer 是竞态条件源
  27. 双 bug 叠加排查：界面完全不可用往往是客户端+服务端独立 bug 叠加，
      必须分别验证
  28. 代码提取重构完整性：提取 main() 后必须确认原入口点完全委托，
      不能在两处保留相同逻辑
  29. delete 恢复 getter 的风险：delete 后如果后续代码仍通过
      this.gd.factions 访问数据会得到 undefined，
      必须用 Object.defineProperty 恢复原始值
  30. mod 客户端 override 版本漂移：不仅 mod-framework/public/ 需要
      版本漂移排查，mods/*/public/ 的 override 文件同样需要
  31. B-type override 上游新逻辑同步：不仅要保留 mod 特有逻辑，
      还必须同步上游新增的功能逻辑（如 _rerollStartAt.clear()），
      版本漂移排查不仅要看行数差异，还要对比上游新增的关键语句

  ── 验证方法论 ──

  32. 两级验证：
      L1 链路追踪：从数据生产→序列化→传输→反序列化→消费→UI渲染，
      逐节点确认字段名/类型/映射关系正确，不是只读代码看逻辑自洽
      L2 运行时测试：实际操作 UI，确认功能表现符合预期
      **L1 通过 ≠ 功能正常**（可能有运行时行为差异），但 L1 不通过则 L2 必定失败
      正确流程：L1 链路追踪 → 修复所有链路断点 → 交给用户 L2 实测确认

  32. 端到端字段名追踪：数据生产方输出的字段名必须逐个与消费方匹配
      例：normalizeSpGroups 输出 turnPid → choiceOverlay 必须读 turnPid
      不能只看"有这个字段"，必须确认字段名完全一致

  33. 序列化往返验证：自定义字段必须追踪完整路径
      设置 → 序列化(freezeDiy) → 存储 → 反序列化 → UI 消费
      每一步都必须保留该字段，任一步丢弃都会静默失效

  34. 多 mod override 完整性：后加载的 override 版本必须逐功能对比原版
      不能只看"包含了主要功能"，必须逐字段/逐逻辑确认无遗漏
      例：20p diy.js 包含了 bonds 扩展但遗漏了 garrisonIds

  35. 数据映射正确性：garrisonIds/kills_a/kills_b 等映射必须对照游戏数据
      验证，不能凭直觉。精锐/非精锐与+1/+2的对应关系必须实测确认

  ── CSS/渲染 ──

  36. pointer-events 穿透设计：父元素 pointer-events: none 时，所有需要
      交互的子元素都必须显式设置 pointer-events: auto。CSS 继承是隐式的，
      容易遗漏。排查"按钮点击不了"时优先检查 pointer-events 链

  37. override 重写函数完整性：override 文件重写上游函数时，必须逐一对比
      函数签名和所有功能分支，不能只保留"自己用到的"模式。被 garrison/band
      等系统调用的公共 API（rollPool/rollItemId 等）必须支持上游的所有
      调用模式。版本漂移排查的第二层不仅要检查"mod 文件是否缺少上游新增
      特征"，还必须检查"mod 重写的函数是否丢失了上游原有功能"

  ── Service Worker / 网络健壮性 ──

  38. SW fetch 必须重试：Service Worker 拦截请求后 fetch 失败直接抛异常
      会导致整个页面生命周期内功能不可用。必须添加重试逻辑，
      重试时用 cache: 'no-store' 绕过浏览器 HTTP 缓存
  39. F5 vs 硬刷新 vs 重开服务器：
      F5 = 普通刷新，SW 仍控制页面，HTTP 缓存协商可能复用异常响应
      硬刷新(Ctrl+Shift+R) = 新 SW 生命周期，绕过所有缓存
      重开服务器 = 新 HTTP 连接，彻底消除服务端异常状态
      偶发问题一旦出现就持续 → 首选检查 SW 缓存和 HTTP 缓存
  40. 二进制文件压缩风险：.bin/.wasm 等大体积二进制文件压缩收益极小
      但增加出错风险。localhost(安全上下文)支持 brotli，LAN IP(非安全
      上下文)只支持 gzip — 压缩方式差异可能导致"只有主机出问题"
  41. 多层重试设计：SW 层重试 + 页面 fetch 层重试 + 场景层重试，
      三层独立重试互不依赖。总重试次数 = 场景层×fetch层×SW层，
      足以覆盖任何瞬态故障

  ── 多轮次/多阶段逻辑 ──

  42. settle 前必须检查轮次：多轮次机制的 settle（终态结算）不能直接
      调用，必须经过轮次检查。当前轮 < 总轮次 → 推进轮次，
      当前轮 = 总轮次 → 执行 settle
  43. 新增 override 比修改原文件更安全：新增独立 override 文件
      （如 unitePhase.js）比修改上游原文件（unite.js）更安全，
      不破坏上游逻辑，上游更新时冲突更少
  44. 分组/分池逻辑先统一决定共享属性：分组逻辑中"先统一决定共享属性、
      再各自生成具体内容"是基本原则。每组独立调用包含随机决策的完整
      生成函数（如 generateDraft）会导致各组结果不一致（如 family 不同）。
      应将随机决策（weightedPick 等）提取到分组循环之外
