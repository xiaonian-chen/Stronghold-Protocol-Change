# 上游更新适配流程（Git 版 · 三层完整流程）
# 最后更新：2026-10-25
# 配套文档：上游更新指南.txt（通俗版）、核心层改动记录-v0.3.1-20p.txt（改动详情）

## 概述

2026-10-24 重构：将 Stronghold-Protocol/ 从"裸文件副本"改为 Git 仓库，追踪上游。
上游通过 GitHub Releases 发布稳定版（打 tag）。

完整更新分三层递进：
  第一层 — 核心合并（Git 自动）
  第二层 — mod-framework 框架兼容性检查
  第三层 — 逐个 mod 适配验证

不再需要旧版的"还原 hook → 更新包 → 重打 hook"三步流程（update-prep.js/update-finish.js 已删除）。

## 新旧流程对比

  旧版（已删除）：
    1. node update-prep.js      还原 7 个 hook 文件为原版
    2. 手动解压更新包覆盖
    3. 启动服务器过 MANIFEST 校验
    4. node update-finish.js    重打 17 处 hook
    5. gen-patches → check-patches → 人工合并 overrides

  新版（当前）：
    1. git fetch upstream --tags && git merge v0.3.x
    2. 框架兼容性确认（patcher / modHook / gen-patches）
    3. 逐 mod 跑 gen-patches → check-patches → 人工合并 → 验证

═══════════════════════════════════════════════════════════
  第二层：mod-framework 框架兼容性检查
═══════════════════════════════════════════════════════════

── 2.1 patcher.js — 运行时文件替换 ──

  文件：mod-framework/lib/patcher.js
  功能：启动时将 overrides/ 目录下的文件替换到 Node.js require 缓存中

  检查方法：
    启动服务器，看控制台是否有 [patcher] 相关警告/错误
    - [patcher] MISSING  → 上游删了某个被覆盖的文件，评估 override 是否废弃
    - 无报错              → patcher 正常

  极端处理：
    如果上游删了某个 overrides 覆盖的文件，而该 override 仍然需要：
    考虑将 override 的内容改为 hook（运行时注入）方式，而非文件替换。

── 2.2 modHook.js — 事件总线 ──

  文件：mod-framework/modHook.js
  功能：提供 on/emit/hook 钩子系统，mod 通过它拦截游戏逻辑

  我们打在上游文件里的 emit 调用：
    scripts/launch.mjs           — modHook 初始化
    server/lobby.js              — lobbyStart, roomCreate, gameMode, businessHook
    server/match/Match.js        — matchStart, matchEnd, bandDraft
    server/match/match/phases.js — phase:* 系列
    server/match/player/economy.js — shopOpen, shopClose
    server/match/finalAssault.js — bossHp
    server/sim/content/bands/meta.js — duckReplace

  每个 emit 行已由 Git 合并保护。如果上游改了 emit 所在函数的签名或
  调用时机，需要人工查看 git diff 确认。

  快速检查：
    cd Stronghold-Protocol
    git diff HEAD~1..HEAD -- server/lobby.js server/match/Match.js \
      server/match/match/phases.js server/match/player/economy.js \
      server/match/finalAssault.js server/sim/content/bands/meta.js

── 2.3 gen-patches / check-patches 工具 ──

  这两个脚本遍历 overrides/ 目录，对每个覆盖的源文件计算 SHA-256，
  与之前生成的 fingerprint.json 比对。

  先跑一次看有无基础报错：
    cd d:\yjw\Stronghold-Protocol-v0.3.1
    node mod-framework/scripts/gen-patches.js 20p

  如果报错（如找不到文件、目录结构变了），说明上游动了目录结构，
  需要微调脚本或 override 路径。

── 2.4 modManager.js — mod 加载器 ──

  启动后看控制台应输出：
    [mod-framework] loading mods...
    [mod:20p] installed
    [mod:clementia] installed
    [mod:dupBand] installed

  如有 mod 加载失败（如某 mod 依赖的函数在上游被删了），会在控制台报错。

═══════════════════════════════════════════════════════════
  附录：mod-framework 核心组件说明
═══════════════════════════════════════════════════════════

  ## patcher.js — 运行时文件替换器

    启动时从各 mod 的 overrides/ 目录读取文件，用完整内容替换
    Node.js require 缓存中的上游文件。

    路径映射规则：
      mods/<mod>/overrides/server/xxx.js → Stronghold-Protocol/server/xxx.js
      mods/<mod>/overrides/shared/xxx.js → Stronghold-Protocol/shared/xxx.js
      mods/<mod>/overrides/public/xxx.js → Stronghold-Protocol/public/xxx.js

  ## modHook.js — 事件总线

    on(name, fn)   注册监听器
    emit(name, ...args) 触发事件
    hook(name, fn) 注册拦截器（可修改/阻止原始行为）

    上游文件中的 emit 调用：
      import modHook from '../../../mod-framework/modHook.js';
      modHook.emit('businessHook', ...);

  ## gen-patches.js — 指纹生成

    为 mod 的每个 override 文件，计算对应上游源文件的 SHA-256，
    存入 mods/<mod>/patches/fingerprint.json。

  ## check-patches.js — 兼容性检查

    读取 fingerprint.json 中的 SHA-256，与当前上游源文件比对，
    输出 [OK] / [CHANGED] / [MISSING] 状态。
